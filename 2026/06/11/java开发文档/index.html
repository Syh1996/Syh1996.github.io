接口

  • 类实现多个接口
    public class 类名 implements 接口1，接口2{}
  • 类继承 and 实现接口
    public class 类名 extends parent implements 接口1，接口2{}

接口中的只能是常量，即使定义变量，继承类也修改不了（默认修饰public static final），公共的部分会抽离到父类抽象类中。

💡 运用场景：类 / 抽象类 / 接口 怎么选？

  • 普通类：最常用。有明确状态（字段）和行为（方法），且不需要被别人扩展时直接用类，如 User、OrderService。
  • 抽象类：当你有一组”共性逻辑 + 部分必须子类实现”时。例：Animal 里 Say() 公共逻辑写在父类，子类只实现 toGo()；或模板方法模式（父类定流程骨架，子类填某一步）。抽象类能持有状态、有构造器，适合表达”is-a”关系（Dog 是 Animal）。
  • 接口：定义”能做什么”的能力契约，不关心谁来实现。例：Comparable（可比较）、Runnable（可运行）、Serializable。一个类可实现多个接口（弥补 Java 单继承）。JDK8+ 接口能写 default 方法，适合给老接口平滑加新方法而不破坏已有实现。
  • 经验法则：描述”是什么/属于哪一类”用抽象类/继承；描述”具备什么能力”用接口；两者可组合，如 class Dog extends Animal implements Pet。

💡 运用场景：内部类到底什么时候用？

  • 静态内部类（最常见）：做”配套类”，尤其 Builder 建造者模式。例：User.Builder 链式构造对象；或把只服务于外部类的工具类收进去，避免污染包。
  • 成员内部类：需要访问外部类实例状态时使用（如迭代器 ArrayList$Itr 内部持有外部 list）。
  • 匿名内部类（旧写法）：写一个”一次性的实现/回调”，比如老式 new Thread(() -> {...})、Swing 按钮点击事件、Comparator 排序。JDK8 之后大多被 Lambda 取代（只有需要多方法或访问外部非 final 变量等少数场景还用它）。
  • 注意：普通内部类会隐式持有外部类引用，可能导致 内存泄漏（Android 经典坑）；不依赖外部实例时优先用 static 内部类。

对象拷贝

💡 前端视角（拷贝）：

  • 浅拷贝 ≈ JS 的对象展开 {...obj} 或 Object.assign({}, obj)：只复制第一层属性，嵌套对象仍是同一个引用。改了拷贝出来的嵌套对象，原对象也会跟着变。
  • 深拷贝 ≈ JS 的 JSON.parse(JSON.stringify(obj))：先把对象序列化成字符串、再解析回新对象，从而得到完全独立的一份。下面用 Gson 实现的 toJson → fromJson 就是 Java 版的 JSON.parse(JSON.stringify())。

深拷贝

💡 前端视角（深拷贝 = JSON.parse(JSON.stringify())）：

Java 用 Gson 做完全一样的事：先 toJson 把对象序列化成 JSON 字符串，再 fromJson 解析成全新的对象实例。两者原理一致——靠”序列化→反序列化”断开引用链。
⚠️ 同样的坑也一致：函数/方法无法被序列化会被丢；Date/循环引用处理方式不同（Gson 能保留类型信息，而 JS 的 JSON.stringify 会把 Date 变成字符串、循环引用直接报错）。生产环境复杂对象建议用更专业的工具（如 Jackson、MapStruct）。

BigInteger

不可变的任意精度整数（java.math.BigInteger），用于超出 long（最大值 9223372036854775807，共 19 位）范围的大整数运算，如订单号生成、雪花ID、RSA 密钥、阶乘、高精度计数等。

为什么需要它：long 只有 64 位，最多约 19 位十进制；BigInteger 内部用 int[] 存储数值，理论上位数仅受 JVM 内存限制，可轻松处理上千位整数。

取值范围与类型转换

  • 取值范围：无固定上下限，仅受内存限制（实践可支持约 6.8 亿位十进制）。
  • 转基本类型（溢出不报错，会静默截断，慎用）：
    • intValue() / longValue() / doubleValue()：溢出时返回截断值（intValue() 超出返回低位）
    • intValueExact() / longValueExact() / shortValueExact() / byteValueExact()（JDK8+）：溢出时抛 ArithmeticException，推荐用于需要精确转换的场景

valueOf 静态工厂方法 vs 普通构造方法

BigInteger 同时提供静态工厂 BigInteger.valueOf(long) 与普通构造方法 new BigInteger(...)，二者区别如下：

维度 BigInteger.valueOf(long) new BigInteger(...)
入参类型 仅 long String / byte[] / (int, Random) 等，功能更丰富
进制解析 不支持 支持，如 new BigInteger("FF", 16) = 255
对象复用 内部缓存 [-16, 16] 范围的值，重复调用返回同一实例 每次都新建对象
性能 对小整数更高效（避免重复分配） 略重
引用相等 == 小范围内 valueOf(x) == valueOf(x) 可能为 true 永远 false

valueOf 内部维护 [-16, 16] 的小整数缓存（源码 MAX_CONSTANT = 16），该范围内取值直接复用同一对象；构造方法永远 new。

重要原则：无论用哪种方式创建，**比较值都必须用 .equals()，绝不能用 ==**（== 只判断引用，缓存仅覆盖 [-16, 16]，边界外必然失效）：

选型建议：手头是 long 数值 → 优先 BigInteger.valueOf(x)，更轻量、可复用；需要字符串/进制解析或生成随机大数 → 用 new BigInteger(...)。

BigDecimal

不可变的任意精度十进制数（java.math.BigDecimal），用于金融/货币/百分比等要求精确计算的场景，避免 double/float 的二进制浮点误差。

核心概念：精度（precision） = 有效数字位数；标度（scale） = 小数点后位数。new BigDecimal("1.00") 的 scale=2，new BigDecimal("1") 的 scale=0，二者 equals 不相等，但 compareTo 相等。

常见案例：金额计算（价格 × 数量 × 折扣）

💡 运用场景：任何”钱 / 比率”都别用 double

  • 订单金额、账户余额、费率、税费、优惠券折扣：这些差一分钱都是事故。永远用 BigDecimal，且用字符串构造。
  • 典型坑：double a = 0.1 + 0.2; 结果是 0.30000000000000004（二进制浮点无法精确表示），直接用于金额就出错；而 new BigDecimal("0.1").add(new BigDecimal("0.2")) 精确等于 0.3。
  • 数据库对应：MySQL 金额字段用 DECIMAL(10,2)（不是 FLOAT/DOUBLE），Java 用 BigDecimal 接，端到端保证精度。
  • 对外传输：前后端通过 JSON 传金额，建议传字符串（"19.99"）而非数字，避免前端 JS 0.1+0.2 同样丢精度（前端同学尤其要注意）。

JDK8 & JDK<8对比

Java 中月份取值不统一，根源在于新旧两套日期 API 的设计差异。简单来说：

  • 旧版 (java.util.Date, Calendar) ：月份从 0 开始，即 0 代表一月，11 代表十二月。
  • 新版 (java.time，Java 8+) ：月份从 1 开始，与我们日常认知一致。
  • 旧版 (Calendar) ： 1 = 星期日 ，2 = 星期一 …… 7 = 星期六（美国标准）。
  • 新版 (java.time) ： 1 = 星期一 ，2 = 星期二 …… 7 = 星期日（ISO国际标准）

💡 前端视角（序列化 = JSON.stringify / JSON.parse）：
把”对象 ↔ 字符串”互相转换，在 JS 里就是 JSON.stringify(obj) 和 JSON.parse(str)。Java 这边只是换了个工具类名字：

Java 工具 等价前端 说明
mapper.writeValueAsString(user)（Jackson） JSON.stringify(user) 对象 → JSON 字符串
mapper.readValue(json, User.class)（Jackson） JSON.parse(json) JSON 字符串 → 对象（**需指定目标类型 User.class**，JS 不用）

关键差异：JS 的 JSON.parse 不需要告诉它”解析成什么类型”（运行时 JS 自己推断）；**Java 是强类型，必须显式传入 User.class 这类”目标 Class”**，反序列化才知道把字段塞进哪个类。这也是为什么 Java 里常看到 new TypeReference<List<User>>(){} 这种”为了告诉编译器泛型类型”的写法。

💡 运用场景：什么时候需要把对象”序列化”？
只要对象要离开当前 JVM 内存（跨进程/跨网络/落磁盘），就需要先变成字节流或字符串：

  • RPC 远程调用：微服务 A 调 B，参数对象要先序列化（JSON / Protobuf / Hessian）再通过网络传输，B 再反序列化。这是微服务通信的基石。
  • Redis 缓存：把 User 对象 writeValueAsString 成字符串存进 Redis，取出来再 readValue 还原。
  • HttpSession / 分布式会话：用户登录信息存 Session（可能序列化到磁盘或共享存储），重启不丢。
  • 消息队列（MQ）：发送给 Kafka/RabbitMQ 的消息体必须是可序列化的字符串/字节。
  • 选型建议：内部服务间用 JSON（Jackson） 最通用可读；追求性能/体积用 Protobuf/Kryo；Java 原生 Serializable 基本不用于网络传输（版本兼容脆弱、体积大）。transient 字段（如密码）不会被序列化，保护敏感数据。

七、Lambda 与 Stream（JDK8+）

💡 前端视角（Stream ≈ 数组的高阶函数链）：

  • Lambda 就是 Java 的”箭头函数”：(a, b) -> a + b ≈ JS 的 (a, b) => a + b；User::getName 这种”方法引用”≈ JS 的 u => u.getName()。
  • Stream 几乎就是 JS 数组的 map / filter / reduce 那一套，只是 Java 是”惰性流水线 + 最后 collect 收尾”：| Java Stream | JS 数组 | 说明 |
    | ———————————— | —————————- | —— |
    | stream().filter(p) | [].filter(p) | 过滤 |
    | stream().map(f) | [].map(f) | 映射 |
    | stream().reduce(0, Integer::sum) | [].reduce(0, (a,b)=>a+b) | 聚合 |
    | Collectors.groupingBy(k) | reduce 累积成对象 | 分组 |
    | flatMap | [].flatMap | 扁平化 |
    | stream().sorted() | [].sort() | 排序 |
  • 关键区别：JS 的 filter/map 立即返回新数组；Java 的 stream() 只是定义”管道”，必须调用 .collect(...)（或 .count()/.sum() 等终结操作）才会真正执行——这就是”惰性求值”。

Optional（避免NPE）

💡 前端视角（Optional ≈ 可选链 ?. 与空值合并 ??）：
Optional 的设计目的 = 把”可能为 null”这件事显式写明，强制你处理。对应到前端：

  • Optional.ofNullable(user).map(User::getAddress).map(Address::getCity).orElse("未知城市")
    ≈ user?.address?.city ?? "未知城市"（JS 的可选链 + 空值合并）。
  • opt.orElse("默认") ≈ value ?? "默认"；opt.orElseGet(() -> heavy()) 才是”为空时才执行默认值函数”（JS 里 ?? 右侧如果是函数调用会先执行，这点 Optional 反而更省）。
  • opt.ifPresent(u -> ...) ≈ if (user) { ... }。
    Optional 帮你把”忘记判空导致 NPE”从运行时崩溃，提前成了”编译期就提醒你处理”。

💡 运用场景：Optional 不是用来当”字段类型”的

  • 正确用法：作为方法返回值，明确告诉调用方”这个方法可能没结果”。例：UserRepository.findById(id) 返回 Optional<User>，调用方被迫处理”找不到”的情况，而不是随手 user.getName() 触发 NPE。
  • 错误用法：不要拿它当实体类的字段/方法参数（会让所有代码都包一层 Optional，反而更啰嗦）；DTO/数据库实体里该 null 就 null。
  • 配合 Stream 的 flatMap：过滤掉空值、把多层嵌套 Optional 摊平，是它最优雅的舞台。

八、反射（Reflection）

💡 运用场景：反射几乎不在业务代码里直接写，但无处不在
反射 = 运行时动态探知/操作类的能力。你写业务时很少手写反射，但你用的每个框架底层都是它：

  • Spring：@Autowired 注入时，Spring 用反射 newInstance 创建 Bean、用反射 set/invoke 注入依赖。
  • MyBatis / JPA：把数据库查出的 ResultSet 通过反射填进你定义的实体类字段。
  • JSON 反序列化：Jackson/Gson 读 JSON 字符串，用反射 new 出对象并 set 每个字段。
  • 动态代理（AOP）：Spring 事务、@Transactional 的代理对象就是反射 + 动态代理生成的。
  • SPI / 插件机制：按配置文件里的全类名 Class.forName("...") 动态加载实现类。
  • 代价：反射比直接调用慢（有安全检查和装箱），且破坏封装。自己业务代码除非做通用框架/工具，否则优先用普通写法。

与 Math 方法同名（abs/sin/sqrt/pow/exp/log…），区别在于 StrictMath 保证跨平台结果逐位一致（基于 fdlibm 标准实现），Math 可能调用平台最优实现（更快但结果略有差异）。

场景：加密、网络协议、跨平台序列化等要求数值可复现时用 StrictMath；普通计算用 Math 即可。

HashMap 原理

  • 数组 + 链表 + 红黑树（JDK8+，链表长度>8且数组长度≥64时树化）
  • 初始容量16，负载因子0.75，扩容为2倍
  • 计算桶位：(n-1) & hash
  • 线程不安全（并发 put 可能丢数据），用 ConcurrentHashMap

Spring IOC/AOP

  • IOC：控制反转，对象创建交给Spring容器管理，通过DI注入依赖
  • AOP：面向切面编程，基于动态代理（JDK代理/CGLIB），用于日志、事务、权限等横切关注点
  • Bean 生命周期：实例化 → 属性赋值 → Aware接口 → BeanPostProcessor前置 → 初始化 → BeanPostProcessor后置 → 使用 → 销毁
  • Bean 作用域：singleton（默认）、prototype、request、session
