接口

  • 类实现多个接口
    public class 类名 implements 接口1，接口2{}
  • 类继承 and 实现接口

💡 运用场景：类 / 抽象类 / 接口 怎么选？

  • 普通类：最常用。有明确状态（字段）和行为（方法），且不需要被别人扩展时直接用类，如 User、OrderService。
  • 抽象类：当你有一组”共性逻辑 + 部分必须子类实现”时。例：Animal 里 Say() 公共逻辑写在父类，子类只实现 toGo()；或模板方法模式（父类定流程骨架，子类填某一步）。抽象类能持有状态、有构造器，适合表达”is-a”关系（Dog 是 Animal）。
  • 接口：定义”能做什么”的能力契约，不关心谁来实现。例：Comparable（可比较）、Runnable（可运行）、Serializable。一个类可实现多个接口（弥补 Java 单继承）。JDK8+ 接口能写 default 方法，适合给老接口平滑加新方法而不破坏已有实现。
  • 经验法则：描述”是什么/属于哪一类”用抽象类/继承；描述”具备什么能力”用接口；两者可组合，如 class Dog extends Animal implements Pet。

💡 运用场景：内部类到底什么时候用？

  • 静态内部类（最常见）：做”配套类”，尤其 Builder 建造者模式。例：User.Builder 链式构造对象；或把只服务于外部类的工具类收进去，避免污染包。
  • 成员内部类：需要访问外部类实例状态时使用（如迭代器 ArrayList$Itr 内部持有外部 list）。
  • 匿名内部类（旧写法）：写一个”一次性的实现/回调”，比如老式 new Thread(() -> {...})、Swing 按钮点击事件、Comparator 排序。JDK8 之后大多被 Lambda 取代（只有需要多方法或访问外部非 final 变量等少数场景还用它）。
  • 注意：普通内部类会隐式持有外部类引用，可能导致 内存泄漏（Android 经典坑）；不依赖外部实例时优先用 static 内部类。

对象拷贝

💡 前端视角（拷贝）：

  • 浅拷贝 ≈ JS 的对象展开 {...obj} 或 Object.assign({}, obj)：只复制第一层属性，嵌套对象仍是同一个引用。改了拷贝出来的嵌套对象，原对象也会跟着变。
  • 深拷贝 ≈ JS 的 JSON.parse(JSON.stringify(obj))：先把对象序列化成字符串、再解析回新对象，从而得到完全独立的一份。下面用 Gson 实现的 toJson → fromJson 就是 Java 版的 JSON.parse(JSON.stringify())。

深拷贝

💡 前端视角（深拷贝 = JSON.parse(JSON.stringify())）：

Java 用 Gson 做完全一样的事：先 toJson 把对象序列化成 JSON 字符串，再 fromJson 解析成全新的对象实例。两者原理一致——靠”序列化→反序列化”断开引用链。
⚠️ 同样的坑也一致：函数/方法无法被序列化会被丢；Date/循环引用处理方式不同（Gson 能保留类型信息，而 JS 的 JSON.stringify 会把 Date 变成字符串、循环引用直接报错）。生产环境复杂对象建议用更专业的工具（如 Jackson、MapStruct）。

BigInteger

不可变的任意精度整数（java.math.BigInteger），用于超出 long（最大值 9223372036854775807，共 19 位）范围的大整数运算，如订单号生成、雪花ID、RSA 密钥、阶乘、高精度计数等。

为什么需要它：long 只有 64 位，最多约 19 位十进制；BigInteger 内部用 int[] 存储数值，理论上位数仅受 JVM 内存限制，可轻松处理上千位整数。

取值范围与类型转换

  • 取值范围：无固定上下限，仅受内存限制（实践可支持约 6.8 亿位十进制）。
  • 转基本类型（溢出不报错，会静默截断，慎用）：
    • intValue() / longValue() / doubleValue()：溢出时返回截断值（intValue() 超出返回低位）
    • intValueExact() / longValueExact() / shortValueExact() / byteValueExact()（JDK8+）：溢出时抛 ArithmeticException，推荐用于需要精确转换的场景
    • signum()：返回 -1 / 0 / 1，比 compareTo(ZERO) 高效
    • toString(int radix)：转指定进制的字符串，默认十进制
    • toByteArray()：转补码字节数组

valueOf 静态工厂方法 vs 普通构造方法

BigInteger 同时提供静态工厂 BigInteger.valueOf(long) 与普通构造方法 new BigInteger(...)，二者区别如下：

维度 BigInteger.valueOf(long) new BigInteger(...)
入参类型 仅 long String / byte[] / (int, Random) 等，功能更丰富
进制解析 不支持 支持，如 new BigInteger("FF", 16) = 255
对象复用 内部缓存 [-16, 16] 范围的值，重复调用返回同一实例 每次都新建对象
性能 对小整数更高效（避免重复分配） 略重
引用相等 == 小范围内 valueOf(x) == valueOf(x) 可能为 true 永远 false

valueOf 内部维护 [-16, 16] 的小整数缓存（源码 MAX_CONSTANT = 16），该范围内取值直接复用同一对象；构造方法永远 new。

重要原则：无论用哪种方式创建，**比较值都必须用 .equals()，绝不能用 ==**（== 只判断引用，缓存仅覆盖 [-16, 16]，边界外必然失效）：

选型建议：手头是 long 数值 → 优先 BigInteger.valueOf(x)，更轻量、可复用；需要字符串/进制解析或生成随机大数 → 用 new BigInteger(...)。

BigDecimal

不可变的任意精度十进制数（java.math.BigDecimal），用于金融/货币/百分比等要求精确计算的场景，避免 double/float 的二进制浮点误差。

💡 运用场景：任何”钱 / 比率”都别用 double

  • 对外传输：前后端通过 JSON 传金额，建议传字符串（"19.99"）而非数字，避免前端 JS 0.1+0.2 同样丢精度（前端同学尤其要注意）。

TreeSet 常见使用与适用需求

TreeSet 基于红黑树实现，特点是元素自动排序（自然顺序或可传入 Comparator），增删查为 O(log n)。**不允许 null**（排序时无比较基准）。

0. 两种排序方式（核心）

TreeSet 的排序只来自两个来源：元素自身实现 Comparable 或 **构造时传入 Comparator**。两者二选一，同时传 Comparator 时以它为准。

① 自然排序（元素实现 Comparable）

② 定制排序（构造时传 Comparator，不用改元素类）

💡 优先用 ② 定制排序：Comparator 写法灵活、不改实体类、可随时换规则；只有排序规则固定且实体类可自由修改时才用 ①。

1. 去重 + 自动排序（最常用）

适用需求：排行榜去重排序、统计指标去重后输出有序集合、按权重/分数排序的标签列表。

2. 范围查询 / 取最值（红黑树的优势）

适用需求：价格区间筛选、时间窗口内数据截取、TopN / 末位淘汰、延迟队列取最早到期任务。

3. 自定义对象排序（必须提供 Comparator 或实现 Comparable）

⚠️ TreeSet 的「去重」依据是 Comparator/Comparable 的比较结果是否为 0，不是 equals！若只按年龄比较，两个同年纪不同名的人会被当作重复。需要严格去重时，Comparator 应把唯一标识也算进去，例如 Comparator.comparing(User::getAge).thenComparing(User::getId)。

泛型（Generics）

泛型是 JDK 5 引入的特性，作用是在编译期做类型检查、避免强制类型转换，把”运行时才暴露的类型错误”提前到编译时。核心符号是 <T>（Type 的占位符，T 可换成任意大写字母）。

0. 为什么需要泛型？（强转的痛点）

在泛型出现之前，集合只能存 Object，取出来必须手动强转，而且编译期不检查类型，错误要到运行时才爆。

三个痛点：

  1. 强转繁琐：每次 get 都要 (类型) 强转，代码啰嗦
  2. 编译期不检查：塞错类型编译器无感知，错误延迟到运行时才暴露（生产环境才崩）
  3. 类型不安全：一个 List 里混了多种类型，取的时候根本不知道该转成什么

用了泛型之后：

对比一目了然：泛型把强转和类型检查交给编译器，既省掉 (String) 强转，又把 ClassCastException 提前到编译期。

💡 如果故意不写泛型（raw type，如 List list），Java 出于兼容会告警但不报错，并默认按 Object 处理，取元素仍需强转——所以新代码务必带泛型。

1. 泛型类（Generic Class）

把类型参数放到类名后面，类内部就可以用这个类型。

对比 raw type（需要强转）：如果不用泛型（裸类型），get() 返回 Object，必须手动强转，否则编译报错：

加了 <String> 之后，编译器记住了”里面装的是 String”，get() 直接返回 String，强转就省掉了——这就是泛型”避免强制类型转换”的含义。

多个类型参数用逗号分隔：class Pair<K, V> { ... }

2. 泛型接口（Generic Interface）

接口也能带类型参数 <T>。实现它时有两种写法，区别只在**”这个 T 到底是谁定”**：

  • 方式一：实现类把 T 定死（写具体类型，如 String）。以后用这个类，泛型就固定了，想存别的类型就得再写一个新类。
  • **方式二：实现类自己还带 <T>**（继续留给使用方定）。这个类更通用，用的时候再告诉它 T 是什么。

常用泛型接口：List<E>、Set<E>、Map<K,V>、Comparator<T>、Supplier<T> 都是泛型接口。

3. 泛型方法（Generic Method）

类型参数放在方法返回值前面、修饰符后面。泛型方法不依赖类是否泛型，普通类也能写。

4. 通配符（Wildcard）

用于”不确定具体类型、只关心范围”的场景，配合 ? 使用： 通配符 ? 只能用在泛型类型的声明中（如 List<?>、Class<?>），不能单独作为参数的类型。

PECS 原则（Producer Extends, Consumer Super）：

  • 只从集合取数据（生产者）→ 用 ? extends T
  • 只往集合放数据（消费者）→ 用 ? super T

不可变集合（Immutable Collections）详解（List / Set / Map）

不可变集合一旦创建，内容、长度都不能再改（增、删、改、排序、clear 全部抛异常），且通常线程安全。适合做常量配置、方法返回值（防止外部篡改）、多线程共享数据。

1. Java 9+ 原生：List.of / Set.of / Map.of

JDK 9 起在接口上直接提供了工厂方法，最简洁，不允许 null 元素（否则 NullPointerException）。

⚠️ List.of(...) / Set.of(...) / Map.of(...) 不接受 null；需要”允许 null 的不可变集合”要用 Collections.unmodifiableList（见第 4 点）。

与 Arrays.asList() 的区别

虽然 Arrays.asList() 常用于快速创建列表，但它不等同于 List.of()。

  • List.of() ：返回一个完全不可变的列表，不支持任何修改操作。
  • Arrays.asList() ：返回一个长度固定但内容可变的列表。你不能增加或删除元素，但可以替换已有元素（即调用 set() 方法）。

因此，如果需要在 Java 8 中实现与 List.of() 完全一致的行为，务必使用 Collections.unmodifiableList() 对 Arrays.asList() 的结果进行包装。

如果你在 Java 8 项目中遇到 List.of 或 Set.of 的编译错误，采用上述替代方案即可解决。

2. Collections.unmodifiableXXX（包装已有集合）

把已有可变集合包一层只读视图。注意：视图只读，但底层原集合仍可改（改了视图跟着变）。

关键点：这是视图（view）不是副本。要真正冻结数据，应先 new ArrayList<>(src) 拷一份再包装。

3. Guava 的不可变集合（推荐做”真·常量”）

Guava 提供 ImmutableList / ImmutableSet / ImmutableMap，创建后完全冻结（连底层都改不了），且允许 null（会直接报错，更安全）。

Guava 不可变集合是真副本：改原 temp 不会影响 frozen，是防御外部篡改返回值的最佳选择。

4. 三者对比与选型

方式 语法 真冻结？ 允许 null 适用场景
List.of / Set.of / Map.of JDK9+ 原生 ✅ 是 ❌ 否 简单常量、少量元素、无 null
Collections.unmodifiableXxx 包装视图 ❌ 仅视图 ✅ 是 临时只读、需保留原集合可写
ImmutableXxx（Guava） 需引依赖 ✅ 是（副本） ❌ 否 返回值防御性拷贝、常量配置、多线程

5. 常见坑

  • **改了就抛 UnsupportedOperationException**：任何增删改（add/remove/set/clear/put）都会抛，不是静默忽略。
  • unmodifiableXxx 不是副本：外层只读、内层可变，原集合一改视图就变——想冻结务必先拷贝。
  • JDK9 of 系列禁 null：放 null 直接启动即 NPE；需要 null 用 unmodifiable 或 Guava 也不行（Guava 也禁 null），只能自己包。
  • 遍历不可变集合本身可正常读：只是不能改；遍历、get、contains、size 都正常。
  • 序列化/做返回值：方法返回不可变集合能让调用方无法破坏内部状态（防御性编程）。

💡 一句话记忆：想要”写死的常量”用 List.of；要”返回给别人但不许他改”用 Guava ImmutableXxx.copyOf；Collections.unmodifiableXxx 只是个只读壳，底层还能动。

IO 流分类总览（基础流 / 包装流）

先建立全局认知再学各个流：Java IO 的流分两大类——基础流（直接连文件）和包装流（套在别的流外面增强功能，装饰器模式）。File 不是流，它只是文件/目录的抽象，管元信息（路径/大小/存在/创建/删除），不负责内容读写；读写内容必须用流去「打开」它。

1. 基础流（直接连文件，共 4 个，所有组装链的底层）

类 方向 单位 用处
FileInputStream 读 字节 读二进制文件（图片/音视频/压缩包/任意文件）的原始字节
FileOutputStream 写 字节 写原始字节到文件（啥文件都能写，配合包装流写文本更方便）
FileReader 读 字符 读文本文件（内部 = InputStreamReader + FileInputStream 的预制组合，用平台默认编码，不能指定编码）
FileWriter 写 字符 写文本文件（内部 = OutputStreamWriter + FileOutputStream 的预制组合，同样不能指定编码）

2. 包装流（套在别的流外面，按功能分 5 类）

类别 类 用处
缓冲流（提速） BufferedInputStream / BufferedOutputStream 包装任意字节流，内置 8KB 缓冲区，减少磁盘调用次数，读写大文件提速明显

3. 组装规则与典型链

组装规则：基础流打底，包装流按需层层套（转换流只能包字节流；缓冲流建议永远套一层）。

要点：

  • File 不是流：只描述文件本身（在哪、多大、存在否），读写内容必须靠流打开它
  • 基础流只有 4 个：字节 2 个（FileInput/OutputStream）+ 字符 2 个（FileReader/Writer），直连文件；其余全是包装流
  • 包装流可自由叠加：如 BufferedReader(new InputStreamReader(new GZIPInputStream(new FileInputStream(file)))) 一条链读 gzip 文本
  • 转换流是唯一桥梁：字节流 ↔ 字符流只能经 InputStreamReader/OutputStreamWriter；FileReader/FileWriter 只是它的预制组合，不能指定编码
  • 只需关闭最外层包装流，其 close() 会级联关闭内部被包装的流

File

File vs NIO.2：java.io.File 是老 API，操作失败只返回 false，不告诉原因；java.nio.file 的 Files 工具类会抛明确异常，且支持原子操作、符号链接、文件属性等，新代码优先用 NIO.2。

FileOutputStream（字节输出流）

FileOutputStream 用于向文件写入字节（图片、压缩包、二进制等），写文本需手动转字节；纯文本推荐用 FileWriter 或 NIO.2 的 Files.write。

要点：

  • 用 try-with-resources 自动关闭流（close 内含 flush），避免资源泄漏；示例 1/2/3 均已采用
  • write(byte[], off, len) 比单字节 write(int) 效率高得多，大文件务必用缓冲
  • 文本场景优先 Files.writeString(path, str)（NIO.2），二进制/流式场景才用 FileOutputStream
  • FileOutputStream 构造时文件已存在会被覆盖（除非 append=true），不会抛异常

FileInputStream（字节输入流）

FileInputStream 用于从文件读取字节（图片、压缩包、二进制等）；读文本需手动转字符。纯文本推荐 Files.readString。

要点：

  • 用 try-with-resources 自动关闭流，避免资源泄漏
  • 务必用带 byte[] 缓冲的 read(buf)，不要用单字节 read()，大文件性能差距巨大
  • read() / read(buf) 返回 -1 表示已读到文件末尾（EOF）
  • 读文本必须手动 new String(bytes, charset) 指定编码，否则用平台默认编码易乱码
  • 大文件避免 readAllBytes()，会一次性撑爆堆内存

字符输入流（FileReader / BufferedReader）

FileInputStream 读文本要手动按编码转字符，容易乱码；字符流以「字符」为单位读写，内部按 Charset 自动编解码，专用于文本文件。

1. FileReader（直接读文本）

2. BufferedReader（按行读取，性能更好）

3. InputStreamReader（字节流 → 字符流桥梁，可指定编码）

4. 文本文件拷贝：边读边写（BufferedReader + BufferedWriter）

核心思路与字节流拷贝一致：read 读出一块字符，立刻 write 写出去，循环到 EOF。字符流额外支持「按行」拷贝，更贴近文本处理习惯。仅用于文本文件，二进制文件请用字节流拷贝（否则会按编码重新解码/编码导致损坏）。

要点：

  • 读文本优先 BufferedReader + FileReader（或指定编码的 InputStreamReader），按行读取最省心
  • 非 UTF-8 文件务必通过 InputStreamReader 显式指定编码，否则平台默认编码易乱码
  • 始终用 try-with-resources 自动关闭流
  • read() / read(buf) / readLine() 返回 -1 / null 表示已到末尾（EOF）

字符输出流（FileWriter / BufferedWriter）

字符输出流以「字符」为单位写出，内部按 Charset 把字符编码为字节，专用于写文本文件。

1. FileWriter（直接写文本）

2. BufferedWriter（按行写出，性能更好）

3. OutputStreamWriter（字符流 → 字节流桥梁，可指定编码）

要点：

  • 写文本优先 BufferedWriter + FileWriter，newLine() 写平台无关换行
  • 非 UTF-8 文件用 OutputStreamWriter 显式指定编码
  • 写完调用 flush()（或依赖 try-with-resources 自动关闭时 flush）确保数据落盘
  • FileWriter(path, true) 追加，FileWriter(path) 覆盖，注意别误覆盖

缓冲流（BufferedInputStream / BufferedOutputStream / BufferedReader / BufferedWriter）

四个 Buffered* 类都是装饰器：包装在基础流（FileInputStream / FileOutputStream / FileReader / FileWriter）外面，内部维护一块默认 8KB 的缓冲区，把「每次 1 字节/1 字符的底层调用」攒成「一批一拨」，大幅减少磁盘/系统调用次数，性能提升明显。实际开发中基础流几乎总是要套一层缓冲流。

1. BufferedInputStream（缓冲字节输入流）

2. BufferedOutputStream（缓冲字节输出流）

3. BufferedReader（缓冲字符输入流）

4. BufferedWriter（缓冲字符输出流）

5. 缓冲流版文件拷贝（字节流，推荐写法）

与裸流拷贝相比，套上缓冲流后 read/write 的底层调用次数大幅减少，且写端自动攒批落盘：

要点：

  • 缓冲流是装饰器，包装基础流使用，本身不直接连文件（new BufferedReader(path) 这种写法不存在）
  • BufferedOutputStream / BufferedWriter **写完必须 flush()**（或依赖 close 自动 flush），否则缓冲区数据不落盘
  • BufferedReader.readLine() / BufferedWriter.newLine() 是按行处理文本的黄金组合
  • mark() / reset() 只有缓冲流（及少数流）支持，裸 FileInputStream 调用会抛 IOException
  • 只需关闭最外层的缓冲流即可，其 close() 会级联关闭内部被包装的基础流
  • 字节缓冲流用于二进制文件；字符缓冲流用于文本文件，别混用

文件拷贝：边读边写（FileInputStream + FileOutputStream）

核心思路：用输入流 read(buf) 读出一块字节，立刻用输出流 write(buf, 0, len) 写出去，循环到 read 返回 -1（EOF）为止。读写在同一循环内完成，边读边写，不占额外全量内存，适合任意大小文件。

要点：

  • 边读边写：read(buf) 与 write(buf, 0, len) 必须在同一循环内，不要先 readAllBytes() 再写——否则大文件会撑爆内存
  • 缓冲大小常用 8KB~32KB；太小则 IO 次数多，太大则浪费内存，按实际调优
  • write(buf, 0, len) 的 len 必须是 read 的返回值，不能直接写 buf.length，否则最后一块会多写无效字节
  • 两个流都放进 try-with-resources，无论哪个抛异常都会自动关闭，避免句柄泄漏
  • 更现代的替代：Files.copy(Path, Path, StandardCopyOption.REPLACE_EXISTING)（NIO.2，一行搞定）

对象流（ObjectInputStream / ObjectOutputStream）

对象流负责序列化（对象 → 字节）与反序列化（字节 → 对象），可把 Java 对象直接存进文件或通过网络传输。被读写的类必须 **implements Serializable**，否则抛 NotSerializableException。

要点：

  • 被序列化类必须 implements Serializable（空接口/标记接口，仅起标识作用）
  • **显式声明 serialVersionUID**：类改了字段后仍能用旧 serialVersionUID 兼容反序列化，否则易 InvalidClassException
  • transient 修饰的字段不参与序列化（如密码、缓存），反序列化后为默认值（引用类型 null）
  • static 字段也不序列化：静态变量属于类，不属于对象实例
  • readObject() 返回 Object 必须强转，且类必须在 classpath 中（否则 ClassNotFoundException）
  • 跨语言/跨版本场景优先用 JSON（如 Jackson），ObjectOutputStream 是 Java 私有格式，仅适合 Java 内部持久化
  • **读取多个对象不要用 while(true) + 捕获 EOFException**，用集合一次性读写更可靠

转换流（InputStreamReader / OutputStreamWriter）

转换流是字节流 ↔ 字符流之间唯一的桥梁：InputStreamReader 把字节输入流转成字符输入流（byte → char），OutputStreamWriter 把字符输出流转成字节输出流（char → byte），两者都能显式指定编码，是读写非 UTF-8 文本、避免乱码的关键。下面给出 JDK 8（手写转换流）与 JDK 11（借助 Files 工具类，内部已封装转换流）两种写法。

要点：

  • 转换流只能包装字节流（FileInputStream / FileOutputStream），不能包字符流；它正是字节与字符世界的唯一入口
  • 编码在转换流处指定（new InputStreamReader(in, StandardCharsets.UTF_8)），务必显式写，别依赖平台默认编码
  • FileReader / FileWriter 是 InputStreamReader/OutputStreamWriter 的预制便捷类，但不能指定编码；需指定编码时必须手写转换流
  • JDK 8：手写 InputStreamReader/OutputStreamWriter + 缓冲流；JDK 11：优先用 Files.newBufferedReader/Writer 或 Files.readString/writeString，更简洁且内部已用转换流
  • 读写文本几乎都该经转换流（或 Files 工具类），直接拿字节流硬转字符串容易乱码

打印流（PrintStream / PrintWriter）

打印流是输出流的包装器，提供 print / println / printf 等便捷方法，写什么类型都自动转成字符串，不用手动 String.valueOf 或转字节。

要点：

  • PrintWriter 面向字符（推荐文本），PrintStream 面向字节（System.out 就是它）
  • 打印流**不抛 IOException**，内部吞掉异常并置错误标志，需主动 checkError() 检查
  • 开启自动刷新只在 println / printf / format 时触发，print 不会
  • printf 用 %n 而不是 \n，保证跨平台换行正确
  • 指定编码时 PrintWriter 要套 OutputStreamWriter（它没有 Charset 构造重载）；PrintStream 可以直接传编码字符串

压缩流（ZipOutputStream）

压缩流是输出流的包装器，写进去的数据会被自动压缩。ZipOutputStream 把多个文件/文件夹打包成 .zip，靠 ZipEntry 区分每个条目。核心三步：**putNextEntry → write → closeEntry**。由简到繁，先压单个文件，再压整个文件夹。

解压流（ZipInputStream / GZIPInputStream）

解压流是输入流的包装器，读取时被自动解压，用法与普通输入流完全一致。

要点：

  • ZipInputStream 靠 getNextEntry() 驱动：返回 null 表示读完了；每读完一个条目必须 closeEntry()

  • 必须做 Zip Slip 校验：解压前用 getCanonicalPath() 确认目标路径在预期目录内，否则恶意压缩包可写入 ../../ 覆盖系统文件
  • 条目名编码要和压缩时一致，new ZipInputStream(in, Charset) 指定；ZipFile 同理
  • GZIPInputStream 没有条目概念，整个流就是一个文件的压缩数据，直接读即可

💡 前端视角（序列化 = JSON.stringify / JSON.parse）：

💡 运用场景：什么时候需要把对象”序列化”？
只要对象要离开当前 JVM 内存（跨进程/跨网络/落磁盘），就需要先变成字节流或字符串：

  • RPC 远程调用：微服务 A 调 B，参数对象要先序列化（JSON / Protobuf / Hessian）再通过网络传输，B 再反序列化。这是微服务通信的基石。
  • Redis 缓存：把 User 对象 writeValueAsString 成字符串存进 Redis，取出来再 readValue 还原。
  • HttpSession / 分布式会话：用户登录信息存 Session（可能序列化到磁盘或共享存储），重启不丢。
  • 消息队列（MQ）：发送给 Kafka/RabbitMQ 的消息体必须是可序列化的字符串/字节。
  • 选型建议：内部服务间用 JSON（Jackson） 最通用可读；追求性能/体积用 Protobuf/Kryo；Java 原生 Serializable 基本不用于网络传输（版本兼容脆弱、体积大）。transient 字段（如密码）不会被序列化，保护敏感数据。

RUNNABLE 可运行 start() 之后；包含”就绪（等 CPU）”和”运行中”两种，JVM 不区分
BLOCKED 阻塞（等锁） 竞争 synchronized 监视器锁失败
WAITING 无限期等待 Object.wait()、join()、LockSupport.park()（需被别人唤醒）
TIMED_WAITING 限期等待 sleep(ms)、wait(ms)、join(ms)、parkNanos（超时自动醒）
TERMINATED 终止 run() 正常结束或抛出未捕获异常

状态流转

  • BLOCKED 只针对 synchronized；用 ReentrantLock 抢锁失败的线程状态是 WAITING/TIMED_WAITING（底层走 LockSupport.park()），排查锁竞争时不要只看 BLOCKED
  • WAITING 与 TIMED_WAITING 的区别只有一个：是否有超时时间；WAITING 只能被别人唤醒，唤醒不了就一直挂着
  • 线程进入 TERMINATED 后**不能再 start()**（重复调用抛 IllegalThreadStateException），要复用请用线程池
  • getState() 只是采样瞬间的状态，排障时通常配合 jstack 看线程栈，能直接看到卡在哪一行、等哪把锁
  • setDaemon(boolean on) 设置为备胎，当主线程结束时，不管当前有没有执行完都结束
  • Thread.yield() 多个线程同时执行时尽可能均匀
  • .join() 多线程本身类似于微任务，添加 join后，可以让当前线程执行完成后再往下执行（FutrueTask包装的除外）

要点：

  • 分工：Runnable = 任务（做什么），Thread = 执行者（谁来做）。实现接口比 extends Thread 更灵活——Java 是单继承，继承 Thread 后就无法再继承别的父类
  • 必须调 start()**：start() 才由 JVM 创建新线程并回调 run()；直接写 t.run() 只是在当前线程里当普通方法执行，不会并发**
  • 函数式接口：Runnable 只有 run() 一个抽象方法，所以支持 Lambda / 方法引用简写；需要复用、带参数、带状态时仍应显式定义实现类
  • 不能抛受检异常：run() 的签名没有 throws，异常只能在方法内 try-catch 处理（InterruptedException 要恢复中断标记）
  • **Callable.call() vs Runnable.run()**：前者有返回值、可声明 throws；后者都没有——需要”结果”或”异常可感知”时选 Callable（方式3）
  • FutureTask 是二合一：同时实现 Runnable + Future，所以既可以直接扔给 Thread，也能当 Future 取结果；线程池 submit(Callable) 内部就是它
  • get() 阻塞：会一直等到任务结束，**强烈建议用带超时的 get(timeout, unit)**，避免线程被无限挂住
  • 异常不在子线程抛出：call() 里的异常被 FutureTask 捕获，只在 get() 时包成 ExecutionException（用 getCause() 取原始异常）；任务被 cancel 后 get() 抛 CancellationException
  • 选型：需要返回值 / 抛异常 / 取消任务用 Callable + FutureTask（方式3）；实际项目中任务都提交给线程池执行，而不是自己 new Thread()；若要组合多个异步结果 / 回调，用 JDK8+ 的 CompletableFuture

Executors 工厂方法（了解原理，生产慎用）

案例要点：

  • execute(Runnable) 无返回值；submit(Callable/Runnable) 返回 Future，可用于取结果、取消、感知异常
  • 提交后要 shutdown()，否则线程一直存活、JVM 不退出；等结果推荐配合 awaitTermination
  • 任务内的异常不会打印到主线程，必须 try-catch 或在 Future.get() 处捕获 ExecutionException

两种线程池的底层参数对比：

线程池 核心线程数 最大线程数 存活时间 任务队列 隐患
newFixedThreadPool(n) n n（固定） 0（不回收） LinkedBlockingQueue（无界，默认 Integer.MAX_VALUE） 任务堆积 →OOM
newCachedThreadPool() 0 Integer.MAX_VALUE（无上限） 60s SynchronousQueue（不存储，直接移交） 高并发下疯狂创建线程 →OOM / CPU 打满

为什么不推荐（阿里规约强制禁止 Executors）

  • newFixedThreadPool 用无界队列，任务无限堆积，最终 OOM，且队列太大时 maxPoolSize 和拒绝策略形同虚设（根本不会触发）
  • newCachedThreadPool 最大线程数是 Integer.MAX_VALUE，相当于无限创建线程，每个线程默认占 1MB 栈内存，高并发下直接 OOM
  • 二者都隐藏了关键参数（队列大小、拒绝策略、线程命名），出问题无法定位、无法防御
  • 正确做法：手动 new ThreadPoolExecutor(...)，显式指定有界队列 + 自定义 ThreadFactory（命名）+ 合理的拒绝策略
