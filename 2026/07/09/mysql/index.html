一、MySQL 定位与整体架构

1.1 MySQL 是什么

MySQL 是关系型、客户端/服务器（C/S）架构的 OLTP（联机事务处理）数据库。所谓”关系型”，指数据以二维表（行/列）组织，表与表之间通过关系（外键/逻辑关联）建模。OLTP 强调高并发、短事务、强一致（与 OLAP 大数据分析相对）。

核心特点：

  • 插件式存储引擎：SQL 解析/优化统一，但数据怎么存、怎么加锁由引擎决定（InnoDB / MyISAM / Memory…）。这是 MySQL 区别于 Oracle/PostgreSQL 的关键架构。
  • ACID 事务（InnoDB）：靠 redo log（持久性）、undo log（原子性/回滚）、锁+MVCC（隔离性）共同实现。
  • B+Tree 索引为主：绝大多数查询性能问题，本质都是”索引有没有用对”。

1.2 逻辑架构（面试/排错必懂）

要点：优化器决定”怎么执行”（选哪个索引、谁做驱动表），它基于统计信息（Cardinality）估算，不是绝对最优——这也是为什么有时要用 FORCE INDEX 或改写 SQL 来引导它。

1.3 存储引擎对比（选型基础）

引擎 事务 锁粒度 外键 聚簇索引 适用场景
InnoDB ✅ 行锁 + 表锁 ✅ ✅ 默认，99% 业务（订单、账户、用户）
MyISAM ❌ 表锁 ❌ ❌ 只读/读多写极少、全文检索老方案、统计计数表
Memory ❌ 表锁 ❌ ❌ 临时结果、缓存表（重启即丢）
Archive ❌ 行锁(insert) ❌ ❌ 归档日志、只插不删改

结论：新项目无脑 InnoDB。它支持事务、崩溃恢复（redo/undo）、行锁高并发、MVCC 无锁读，几乎全面优于 MyISAM。

三、数据类型（最易被低估、最影响性能与正确性）

为什么数据类型这么重要？ 选错类型不只是”不优雅”，而是真实的生产事故：用 FLOAT 存金额，对账时发现少了 1 分钱（浮点误差）；用 VARCHAR(255) 存手机号，索引比 CHAR(11) 大好几倍，百万级表查询慢 3 倍；用 DATETIME 存跨国用户时间，结果不同时区用户看到的时间全是错的。下面每种类型都会告诉你：在什么业务场景用、为什么这么选、选错了会怎样。

💡 学习建议：看到一个类型时，先想”我的项目里哪个字段该用它”——把它和你正在开发的真实业务对应起来，而不是死记字节数。

3.1 数值类型

整数（精确，无误差）

类型 字节 有符号范围 无符号范围 (UNSIGNED)
TINYINT 1 -128 ~ 127 0 ~ 255
SMALLINT 2 -32768 ~ 32767 0 ~ 65535
MEDIUMINT 3 -8388608 ~ 8388607 0 ~ 16777215
INT / INTEGER 4 -2147483648 ~ 2147483647 0 ~ 4294967295
BIGINT 8 -2^63 ~ 2^63-1 0 ~ 2^64-1
  • UNSIGNED：非负且范围翻倍（如自增主键、年龄、数量用 UNSIGNED 更省）。
  • 显示宽度（如 INT(11)）：仅影响 zerofill 显示，不影响存储与取值范围，8.0 已不推荐使用 INT(11)，直接写 INT。
  • 自增主键：INT UNSIGNED AUTO_INCREMENT 约 42 亿上限，BIGINT UNSIGNED 几乎无限。

💡 真实案例：整数类型怎么选？

选型口诀：能确定范围的就选最小类型（TINYINT < SMALLINT < INT < BIGINT），每少一个级别省 1~4 字节 × 数据量 = 百万级省出几 MB 索引空间。

定点数（金额必须用这个）

类型 说明 精度
DECIMAL(M,D) 精确小数，以字符串形式存储 M 总位数(165)，D 小数位(030)
NUMERIC DECIMAL 的同义词 同

FLOAT/DOUBLE 是二进制浮点，有误差：0.1 + 0.2 ≠ 0.3（0.30000000000000004）。金融、计费、对账场景一律 DECIMAL。

💡 真实案例：FLOAT vs DECIMAL 的差距

使用场景：订单金额、会员余额、佣金、税费、汇率——凡是涉及”钱”的，全部用 DECIMAL。FLOAT/DOUBLE 只用在科学计算（如传感器温度、GPS 经纬度等不要求精确到分的场景）。

浮点（仅用于科学/非精确度量）

类型 字节 有效位数
FLOAT 4 ~7 位十进制
DOUBLE 8 ~15 位十进制

位类型

  • BIT(M)：存储位串（0~64 位），适合权限位标记；用 b'101' 字面量。查询返回二进制，需用 BIN()/CAST() 转换。

3.2 字符串类型

类型 说明 长度上限
CHAR(N) 定长，N 0~255，不足右补空格 固定 N 字符
VARCHAR(N) 变长，N 065535(受行 65535 字节限制)，12 字节记长度 变长
TINYTEXT/TEXT/MEDIUMTEXT/LONGTEXT 大文本 255 / 64KB / 16MB / 4GB
TINYBLOB/BLOB/… 二进制大对象 同上
ENUM('a','b',...) 枚举，存 1/2/3 整数，省空间 最多 65535 个值
SET('a','b',...) 集合，位掩码 最多 64 个
JSON (8.0) JSON 文档，校验格式、可路径查询 ——

CHAR vs VARCHAR 选择原则：

  • CHAR：长度固定且短（如手机号 CHAR(11)、UUID 去横杠 CHAR(32)、国家码 CHAR(2)、MD5 CHAR(32)），且对比更快（定长无碎片）。
  • VARCHAR：绝大多数业务字段（用户名、地址、标题），按需分配、省空间。
  • TEXT：不进行、单独存、不能建普通索引但可建前缀索引；大字段建议拆表，避免拖慢主表回表。

💡 真实案例：一个用户表的字符串字段选型

使用场景总结：手机号/身份证/MD5/UUID → CHAR；姓名/标题/URL → VARCHAR；文章正文/评论详情 → TEXT（但建议拆到副表）。

陷阱：VARCHAR 的 N 是字符数不是字节数。utf8mb4 下每个字符最多 4 字节，所以 VARCHAR(255) 最多占 255×4+2 ≈ 1022 字节。一个 InnoDB 行所有列总字节数上限 65535，所以一个表不能有太多长 VARCHAR。

ENUM/SET 注意：

  • 优点：存整数省空间、自带校验。
  • 缺点：枚举值修改需 ALTER TABLE（DDL，8.0 原子但仍有成本）、排序按存储序号而非字母序、部分 ORM 不友好。现代实践更推荐用 TINYINT + 代码字典，或 VARCHAR + 应用层校验。

3.3 日期时间类型

类型 字节 范围 时区敏感 说明
DATE 3 1000-01-01 ~ 9999-12-31 否 仅日期
TIME 3 -838:59:59 ~ 838:59:59 否 可表示时长
DATETIME 8 (5.6+) 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59 否 与时区无关，原样存原样取
TIMESTAMP 4 1970-01-01 00:00:01 ~ 2038-01-19 03:14:07 (UTC) 是 存UTC，按会话时区转换；自动更新
YEAR 1 1901 ~ 2155 否 年份

DATETIME vs TIMESTAMP 选型：

  • 需要跨时区一致（如全球用户活动时间、审计时间）→ 用 TIMESTAMP（随 session time_zone 转换，存 UTC）。
  • 需要大范围/不随时区漂移（如生日、历史归档、未来超过 2038 的时间）→ 用 DATETIME。
  • 2038 年问题：TIMESTAMP 上限 2038-01-19，长期系统慎用。

💡 真实案例：DATETIME vs TIMESTAMP 选型场景

选型口诀：全球化跨时区 → TIMESTAMP（但注意 2038 年问题！）；国内项目/不需时区转换 → DATETIME；只要日期不要时间 → DATE。

3.4 类型选择总原则（资深经验）

  1. 越小越好：能用 TINYINT 别用 INT，能用 INT 别用 BIGINT（索引更小、内存更少、缓存更多行）。
  2. 越简单越好：整型比字符串快；能用整型表示（如状态码）就不用字符串。
  3. 避免 NULL 列：NULL 使索引/统计/比较更复杂（需要额外位标记）；可用 NOT NULL + 默认值替代（如字符串 ''、数值 0）。主键必须 NOT NULL。
  4. **IP 地址用 INT UNSIGNED**（而非 VARCHAR(15)）：INET_ATON('127.0.0.1') ↔ INET_NTOA(ip)，省 75% 空间且可范围查询。
  5. JSON（8.0）：适合结构不稳定、无需频繁按内部字段聚合的属性（如商品扩展属性）；但频繁查询/过滤的字段应独立成列 + 索引，别全塞 JSON。

四、约束、主键与表设计

4.1 六种约束

约束 关键字 作用
主键 PRIMARY KEY 唯一标识一行，非空且唯一，InnoDB 用它组织数据（聚簇索引）
非空 NOT NULL 列不可为空
唯一 UNIQUE [KEY] 值唯一（允许 NULL，多个 NULL 不冲突）
默认值 DEFAULT 插入未指定时填充
外键 FOREIGN KEY ... REFERENCES 参照完整性（子表值须存在于父表）
检查 CHECK (expr) 8.0 真正生效，如 CHECK (age >= 0)

4.2 主键设计（重要）

  • **自增 BIGINT**：最经典，插入顺序追加、聚簇索引无碎片、性能好。缺点：分库分表时易冲突、可被遍历猜测 ID。
  • UUID：全局唯一，但无序 → 聚簇索引频繁页分裂、写入性能差；若用请用 CHAR(32) 去横杠或 8.0 UUID_TO_BIN(uuid, 1)（交换时间低位，提升有序性）。
  • 雪花 ID（Snowflake）：64 位趋势递增、分布式唯一，兼具自增的有序性与分布式的唯一性，生产首选。
  • 业务联合主键（如订单明细 (order_id, item_id)）：仅在确属自然键且无性能顾虑时使用，否则用代理主键 + 唯一索引。

外键的取舍：外键保证一致性但带来写锁耦合、跨表级联成本、分库分表不可用。互联网高并发系统多在应用层维护参照完整性，而非数据库外键。

💡 真实案例：外键用不用？两种做法对比

使用场景：银行/ERP/政务等对数据一致性”零容忍”的系统 → 考虑外键；电商/社交/内容平台等高并发互联网系统 → 不用外键，靠代码+索引+定时数据校验保证一致性。

4.3 范式与反范式（冗余设计）

  • 三范式：消除冗余、避免更新异常（适合写多、一致性要求高的核心表）。
  • 反范式/冗余列：把频繁 JOIN 的字段冗余到主表（如订单表冗余 user_name），以空间换 JOIN 性能（适合读多、报表、宽表）。
  • 实践：核心交易表遵循范式；统计/展示宽表适度冗余。本质是读写比的权衡。

💡 真实案例：范式 vs 反范式——订单表要不要冗余用户名？

使用场景：

  • 遵守范式：核心交易表（用户表、账户余额表）—— 数据不重复，改一处即全局生效。
  • 适度冗余：订单列表页、商品详情页等”读多写少、经常需要关联展示”的场景 —— 用冗余字段省掉 JOIN，接受”改名时多更新一张表”的写代价。
  • 经验法则：如果一个 JOIN 在高频查询中反复出现，且被 JOIN 的字段几乎不变（如用户名、商品名），就值得冗余。

五、DDL（数据定义语言）

5.1 建库

字符集铁律：全程 utf8mb4（真正的 4 字节 UTF-8，支持 emoji 与所有中文）。MySQL 的 utf8 是伪 UTF-8（仅 3 字节），存不了 emoji 和部分生僻字。排序规则 _ci 大小写不敏感、_bin 二进制精确（需区分大小写如验证码/令牌用 _bin）。

7.2 WHERE 条件与 NULL 陷阱

NULL 三大铁律：

  1. NULL 不等于任何值，包括它自己：NULL = NULL 结果为 NULL（非 true）。判断空用 **IS NULL / IS NOT NULL**。
  2. WHERE col != 'x' 不会返回 col 为 NULL 的行（NULL 参与比较结果未知，被当作 false 过滤掉）——这是最隐蔽的漏数据 bug。
  3. NOT IN (子查询) 若子查询含 NULL，整个结果可能为 NULL（返回空集）。用 NOT EXISTS 替代更安全。

7.3 LIKE 模糊查询

前缀 % 在最左才走索引；前后都有 % 必全表扫描。需要”包含/后缀”检索请用全文索引（FULLTEXT）或 ES。

7.4 排序 ORDER BY

  • 排序字段有索引且顺序一致 → 索引有序，免排序（Extra 无 Using filesort）。
  • 无索引或 ORDER BY 与索引顺序不符 → Using filesort（内存/磁盘排序，大数据量慢）。LIMIT 常配合 ORDER BY 主键做深度分页优化（见 §12.1）。

7.5 分组聚合 GROUP BY + HAVING

COUNT 三兄弟（高频考点）：

写法 含义 是否计 NULL 行 InnoDB 实现
COUNT(*) 行数 计（NULL 整行也算） 全表/索引扫描计数
COUNT(1) 行数 计 等价于 COUNT(*)
COUNT(col) col 非 NULL 的行数 不计 col 为 NULL 的行 扫描 col

结论：COUNT(*) 与 COUNT(1) 在 InnoDB 性能基本无差，语义最清晰，**统计行数用 COUNT(*)**。COUNT(col) 是”非空计数”，语义不同不要混用。MyISAM 的 COUNT(*) 有缓存总数（无 WHERE 时 O(1)），InnoDB 无，需扫表或靠二级索引。

7.6 多表 JOIN

JOIN 核心认知（资深必懂）：

  • 驱动表：MySQL 用嵌套循环（Nested-Loop）：先取驱动表（外表）的行，再用关联列去被驱动表查。
  • 优化器选驱动表依据预估行数，通常小表驱动大表更优；确保被驱动表的关联列有索引（否则退化成”全表 × 全表”灾难）。
  • ON vs WHERE：
    • INNER JOIN 中 ON 与 WHERE 过滤效果等价（优化器会下推）。
    • LEFT JOIN 中把右表过滤条件放 ON**（保留左表所有行）还是 WHERE（过滤后只剩匹配行，等价于 INNER）语义完全不同**，务必分清。

八、索引（性能命脉，重中之重）

一句话：大多数 MySQL 性能问题 = 索引没建对 / 没用上。资深工程师的核心竞争力之一，就是”看一眼 SQL 和表结构，能预判它会不会慢、慢在哪”。

8.1 为什么索引快（B+Tree）

InnoDB 默认索引是 B+Tree（多路平衡树）：

  • 数据按主键顺序存在叶子节点（聚簇索引，Clustered Index），叶子间用双向链表串联 → 范围查询/排序极快。
  • 树高通常 3~4 层即可存千万亿级数据，一次查询只需 34 次磁盘 IO。
  • 二级索引（Secondary）叶子存 (索引列, 主键值)，查到主键后再回表取整行（这就是”回表”开销）。

💡 真实案例：没有索引 vs 有索引——百万数据查询对比

使用场景：只要你的 WHERE/JOIN ON/ORDER BY 用到了某个列，且表数据超过几千行，就应该考虑给它建索引。不建索引 = 每次查询都要扫全表（想象从一本 1000 页的书里找一个词，没有目录只能一页页翻）。

8.2 索引类型

类型 说明 关键字
普通索引 无唯一约束 INDEX / KEY
唯一索引 值唯一（允许 NULL） UNIQUE KEY
主键索引 特殊的唯一非空聚簇索引 PRIMARY KEY
组合索引 多列联合 INDEX idx(a,b,c)
前缀索引 对长字符串前 N 字符建索引 INDEX idx(col(20))
全文索引 分词检索 FULLTEXT
空间索引 地理 SPATIAL
覆盖索引 查询列全在索引中，无需回表 查询利用组合索引

8.3 创建/查看/删除

8.4 最左前缀原则（组合索引的灵魂）

组合索引 (a, b, c) 相当于建立了 (a)、(a,b)、(a,b,c) 三个有效前缀。查询必须从最左列开始且连续才能用上索引：

查询条件 是否用索引 说明
WHERE a=1 ✅ (a) 用最左列
WHERE a=1 AND b=2 ✅ (a,b) 连续前缀
WHERE a=1 AND b=2 AND c=3 ✅ (a,b,c) 全用
WHERE b=2 ❌ 跳过最左列 a
WHERE a=1 AND c=3 ✅ 仅 (a) a 用索引，c 在索引内过滤但非前缀
WHERE a>1 AND b=2 ✅ 仅 a 范围查询(a)后的列(b)失效

组合索引列顺序设计原则：区分度高的列放前面（如 user_id 放前，status 放后），且把最常用于等值过滤的列放最左。

💡 真实案例：组合索引的最左前缀——“查某用户某时间段的订单”

使用场景：只要你的查询是”A=某值 AND B 范围/排序”的模式，就建 (A, B) 组合索引。常见于：查某用户的订单/消息/日志（按时间排序）、查某商户的交易（按金额/时间排序）。

8.5 索引失效（必背场景）

以下情况会导致优化器放弃索引、全表扫描：

  1. 对索引列用函数/运算：WHERE DATE(created_at)='2026-07-09'（应改为范围 >= AND <）；WHERE amount*1.1 > 100。
  2. 隐式类型转换：列是 VARCHAR，却 WHERE phone = 13800000000（传数字）→ MySQL 对列做 CAST，索引失效。务必类型匹配。
  3. 前导 % 模糊：LIKE '%abc'。
  4. OR 连接非索引列：WHERE a=1 OR b=2（b 无索引则全表）。可改为 UNION 或给 b 加索引。
  5. 不等于 / NOT IN / IS NOT NULL（通常）：选择性差时优化器认为全表更划算。
  6. 优化器认为全表更快：当命中数据超过约 20%~30% 时，优化器往往选全表扫描（回表成本高）。此时覆盖索引或 FORCE INDEX 可引导。

💡 真实案例：索引失效的”坑”——函数包裹索引列

记忆口诀：索引列上不能”加工”（函数、运算、类型转换），否则索引失效。查日期段永远用 >= AND <，不用 DATE()/YEAR() 包裹。

8.6 覆盖索引（性能优化杀手锏）

“覆盖索引”= 查询所需的所有列都包含在某个索引中，无需回表。

实战：高频只读查询可建宽组合索引覆盖常用列（以空间换免回表的性能）；SELECT * 几乎不可能被覆盖，尽量只查需要的列。

8.7 解读执行计划 EXPLAIN（排错核心）

字段 含义 / 关注点
id 执行顺序（大→先，相同则自上而下）
select_type SIMPLE / PRIMARY / SUBQUERY / DERIVED 等
type 访问类型，越靠前越好：system > const > eq_ref > ref > range > index > ALL。**ALL=全表扫描（需警惕）**
possible_keys 可能用的索引
key 实际用的索引（NULL=没用上，要查为什么）
key_len 索引用到的字节数（判断组合索引用了几列）
rows 预估扫描行数（越小越好）
Extra 关键提示：Using index(覆盖) / Using where(回表后过滤) / Using index condition(ICP) / Using filesort(需排序，慢) / Using temporary(用临时表，慢)

排错套路：type=ALL 或 rows 巨大或 Extra 出现 Using filesort/Using temporary → 基本就是慢查询，回去检查 WHERE/JOIN/ORDER BY 是否命中索引。

8.8 索引设计 checklist（资深经验）

  • ✅ WHERE / JOIN ON / ORDER BY / GROUP BY 用到的列优先建索引。
  • ✅ 高基数（Cardinality）列放组合索引前面。
  • ✅ 用覆盖索引消除回表；少 SELECT *。
  • ✅ 长字符串用前缀索引 col(20)，并权衡前缀长度与选择性。
  • ❌ 不过度索引：每个索引拖慢写入、占空间、增加优化器选择成本。写多读少的表索引从简。
  • ❌ 不在低基数列（如 gender 只有 2 值）单独建索引（选择性差，优化器多半不用）。
  • ❌ 不建”永远用不上”的索引（用 sys.schema_unused_indexes / 8.0 隐藏索引验证后清理）。

九、事务与锁（并发正确性）

9.1 ACID

  • A 原子性：事务内操作要么全成功要么全失败（undo log 支持回滚）。
  • C 一致性：数据从一个一致状态到另一个（业务约束由应用+DB 共同保证）。
  • I 隔离性：并发事务互不干扰（靠锁 + MVCC）。
  • D 持久性：提交后数据永久保存（redo log + 刷盘）。

9.2 事务控制

事务内注意：DDL（CREATE/ALTER/DROP/TRUNCATE）会隐式提交当前事务；事务中混 DDL 是常见坑。

9.3 四种隔离级别与并发异常

隔离级别 脏读 不可重复读 幻读 说明
READ UNCOMMITTED（读未提交） ❌可能 ❌可能 ❌可能 能看到别人未提交的数据，几乎不用
READ COMMITTED（读已提交） ✅避免 ❌可能 ❌可能 Oracle 默认，每次读最新已提交
REPEATABLE READ（可重复读） ✅ ✅ ✅(靠间隙锁) MySQL InnoDB 默认
SERIALIZABLE（串行化） ✅ ✅ ✅ 加读锁，性能差，并发低
  • 脏读：读到别的事务未提交的数据（可能回滚）。
  • 不可重复读：同一事务内两次读同一行，结果不同（被别的事务UPDATE了）。
  • 幻读：同一事务内两次范围查询，行数不同（被别的事务 INSERT/DELETE 了）。

InnoDB 如何解决可重复读 + 幻读：靠 MVCC（多版本并发控制） 让普通读（快照读）看到事务开始时的快照（解决不可重复读）；靠 Next-Key Lock（记录锁 + 间隙锁） 在范围查询时锁住间隙，防止别的事务插入（解决幻读）。所以 InnoDB 在 RR 下不会发生幻读。

9.4 锁机制（InnoDB）

锁 说明
共享锁 S（LOCK IN SHARE MODE / FOR SHARE） 读锁，多个事务可同时持有，互斥写
排他锁 X（FOR UPDATE / UPDATE/DELETE/INSERT） 写锁，独占
意向锁 IS/IX 表级，表明”事务将要在某些行加 S/X 锁”，避免行锁与表锁冲突
记录锁 Record Lock 锁单行
间隙锁 Gap Lock 锁索引记录间的”间隙”，防插入
Next-Key Lock 记录锁 + 间隙锁（RR 默认，解决幻读）

死锁：两个事务互相等待对方持有的锁。InnoDB 会检测并回滚其中一个（代价小者）。避免方法：事务尽量短、按固定顺序访问多张表/多行、降低隔离级别/锁粒度、及时提交。

💡 真实案例：死锁是怎么发生的？

解决办法：让所有事务按 id 从小到大的顺序更新（如都先锁 id=1 再锁 id=2），就不会互相等待。代码里捕获死锁异常后重试即可（InnoDB 只回滚一个）。

长事务危害（生产大忌）：持有锁和 undo 版本时间长 → 阻塞他人、undo 膨胀、主从延迟、甚至 OOM。务必缩小事务边界，别在事务里调外部接口/睡大觉。

12.2 树形结构（分类/组织架构）

使用场景：电商的商品分类（一级分类→二级→三级）、公司组织架构（集团→事业部→部门→组）、评论的回复树、文件夹目录——任何”有父子层级关系”的数据都是树形结构。核心问题：怎么在关系型表里存树、怎么高效查某节点的所有子孙？

其它方案：路径枚举（存 '/1/3/10' 全路径，LIKE 查子孙）、闭包表（另建关系表，查子树最快但写入复杂）。层级浅/变更少选邻接表+递归 CTE 最简洁。

12.3 行转列 / 列转行

使用场景：报表展示。数据库里成绩是”一行一条记录”（张三-语文-90、张三-数学-85），但报表/前端需要一行展示一个学生的所有科目（张三 | 90 | 85 | 78）。这就是”行转列”。反过来，有时宽表需要转成长表做分析/导入，就是”列转行”。

12.4 连续登录天数 / 留存

使用场景：运营分析。产品经理想知道”用户连续登录了多少天”来做签到奖励/活跃度分析；或计算”次日/7日/30日留存率”判断产品粘性。这是游戏、社交、教育类 App 最常见的数据需求。

注意：含子查询的 DELETE 在 MySQL 中不能直接 DELETE FROM t WHERE id NOT IN (子查询同表)，需套一层派生表（如方法2的内层 t）规避 “不能先 SELECT 再 UPDATE 同表” 限制。

12.8 缺失日期补 0（报表常用）

使用场景：做报表/图表时，如果某天没有数据（如周末没订单），直接查会”跳过”那天，导致前端折线图断裂。解决方案：先生成一组连续日期，再 LEFT JOIN 实际数据，无数据的天自动补 0。运营日报、销售趋势图、活跃用户曲线都需要。

十三、性能优化清单（排障 SOP）

  1. 开启并分析慢查询日志： 用 pt-query-digest 聚合慢日志，找出高频/高耗时 SQL。
  2. EXPLAIN 每一类慢 SQL（见 §8.7），看 type/key/rows/Extra。
  3. 索引先行：按 §8.4~8.8 原则补/调索引，优先覆盖索引。
  4. 消灭全表扫描与 filesort/temporary：改写 SQL、加合适索引、SELECT 只取所需列。
  5. SQL 改写：
    • 避免 SELECT *；避免 ORDER BY RAND()；
    • IN 元素过多改 JOIN 临时表；
    • COUNT(*) 大表用估算/EXPLAIN 的 rows，或冗余计数表；
    • 深分页用游标/延迟关联（§12.1）。
  6. JOIN 优化：确保被驱动表关联列有索引；小表驱动大表。
  7. 批量操作：INSERT 多值、批量 UPDATE 用 CASE WHEN 一次性改，减少交互。
  8. 连接池：合理设置最大连接数（如 HikariCP maximumPoolSize ≈ DB 核数*2），避免连接耗尽。
  9. 表结构：类型最小化、避免大字段在主表、定期 OPTIMIZE/ANALYZE TABLE 更新统计信息。
  10. 架构层：读写分离（主写从读）、分库分表（ShardingSphere）、缓存（Redis 扛读热点）、ES 扛检索。

十四、字符集与排序规则（乱码根因）

  • utf8mb4 是真正 UTF-8（4 字节），支持 emoji 与全部中文；**utf8(utf8mb3) 仅 3 字节**，存 emoji 报错。
  • 三级一致：库、表、列、连接字符集都要一致，否则乱码。连接串加 ?useUnicode=true&characterEncoding=utf8mb4。
  • 排序规则：utf8mb4_general_ci（快、精度略低）、utf8mb4_0900_ai_ci（8.0 默认，ai=口音不敏感、ci=大小写不敏感）、utf8mb4_bin（二进制精确，区分大小写，适合令牌/校验码）。
  • 常见乱码排查：客户端编码 ≠ 服务端编码、列单独指定了不同字符集、emoj‍i 用 utf8 存。

十五、安全与规范

15.1 SQL 注入（必防）

铁律：任何用户输入必须参数化（? 占位），禁止拼接。ORM（MyBatis #{} 是预编译，${} 是拼接，禁用 ${} 接用户输入）。最小权限账号、关闭 FILE 等危险权限。

15.2 命名与开发规范（团队共识）

  • 表/字段用小写蛇形 user_order / created_at；表名单数或复数统一。
  • 必备：id 主键、created_at、updated_at；逻辑删除用 deleted/is_deleted 而非物理删。
  • 每个字段加 COMMENT；表加 COMMENT。
  • 索引命名：idx_字段 / uk_字段 / pk_。
  • SQL 关键字大写，便于阅读与区分。

十六、备份与恢复（DBA 底线）

生产必须：定期全量 + binlog 增量 + 异地/云存储 + 定期恢复演练。没演练过的备份 = 没有备份。
